# UX レベルデザイン（学習曲線）

ゲームの**学習曲線（時間軸）**を設計する。  
進行の原理（アンロック2軸＝コマンド解放 / プログラムキャパシティ）は [docs/README.md](../README.md) のコンセプト・スコープで掲げた背骨であり、ここではその**適用＝学習曲線としてどう並べるか**を書く。

> 本ドキュメントの Chapter 表は **WIP（暫定）**。

---

## ゲーム設計の進め方

**プレイヤーの体験(UX)から設計を始め、そこから画面・遷移（UI）を導出する**。

次の順で設計する:

1. **UX ループ**: プレイ中に繰り返す行為の単位（＝コアループ）
2. **UX 要素**: 各ループ内の各ステップで何を見て・何を触るか（＝状態・情報・操作などの体験の構成要素）
3. **UI コンポーネント**: UX 要素を提供する設計単位
4. **UI 画面**: UI コンポーネントをどう画面に配置し、画面間をどう遷移させるか

1+2（UX）を本ドキュメント、3+4（UI）を [ui-screen-design.md](./ui-screen-design.md) で整理する。

## Tier 表: コアループは「育つ」

UX ループは1つではなく、進行に沿って**やることのテーマそのものが成長する**。  
この成長は「**ゲームプレイの複雑化の勾配**」として捉えられ、各段を **Tier**（序数）と呼ぶ。

| Tier   | テーマ   | 敵パターン             | ループの形                    | ねらい（教えること）       |
| ------ | -------- | ---------------------- | ----------------------------- | -------------------------- |
| Tier 1 | **行動** | 動かない的             | 組む → 観戦                   | 自キャラの動かし方         |
| Tier 2 | **反応** | 基本動作のみ           | 組む → 観戦                   | 動く敵キャラへの対応       |
| Tier 3 | **読解** | 動作・**コード公開**   | **読む** → 組む → 観戦        | 敵コードを読んで動きを推測 |
| Tier 4 | **推理** | 動作・**コード非公開** | **観察 → 推理** → 組む → 観戦 | 振る舞いからコードを推測   |

ポイント:

- **各 Tier 境界＝増分ちょうど 1 つ**: 1 つの境界で新概念を複数同時に積まない（例: 「動く」と「コード公開」は別 Tier に分ける）
- **「反応」は「読解／推理」の前段**: ソースを読まず今の状態に即応する方が読解・推理より軽く、動く敵への最初の一歩になる。撃ち返す相手を要する負荷攻撃/BP もこの段が自然な置き場
- **コードの開示（公開 → 非公開）が事実上の第3の調整軸**: ブロック／CP に続く難度カーブになる

### 3 階層（Tier / Chapter / Stage）と SSOT

各 Tier は、さらに **Chapter** に細分化し、新しい UX 要素を 1 つずつ足して複雑化の勾配を緩やかにする。  
そして、各 Chapter は 1 つまたは複数の **Stage** で構成する。  
**レベルデザイン（本ドキュメント）が決めるのはこの Chapter まで**とし、Stage の SSoT は実装側とする。

- **Tier**: テーマ（ループの形）の単位。上述の 4 段
- **Chapter**: Tier 内で**新要素（＝新しい UX 要素）を 1 つ**導入する単位。それを提供する UI が足されていく
- **Stage**: Chapter 内の具体的な 1 プレイの単位。新要素は足さず、同じ要素を反復・変化させる

## B面の位置づけ

B面（教材）は、**完全に任意の「おまけ」＝見ても見なくてもよい**。  
性格は**種明かし＝解説**で、A面の裏にある実際の技術・コンピュータサイエンス概念を明かす。  
学習曲線は A面の Tier／Chapter 進行そのもの（**概念の体験**）が担い、B面はその裏にある補足（**ラベルの付与**）にすぎない。

**原則**:

- **B面は進行をゲートしない**: B面を一切見なくても、A面だけで全ステージをクリアできる
- **B面は“追加報酬”であって“補助”ではない**: 「"HP 0 での撃破"の正体は"ヒープ枯渇による OOMKilled"」という**実用語への橋渡しが価値**で、ゲームプレイには直接役に立たない（プレイ補助のヒントとは別軸で、混同するとブレるので注意）
- **opt-in**: 順次解放するが押しつけない。UX 上は **A面に従属する控えめなアフォーダンス**であって、プレイと対等なトップ扉ではない

**接続の単位（どこに・いつ出すか）**:

- 対応関係: **1 Chapter ＝ 1 概念 ＝ 1 教材**。各 Chapter が導入する A面概念に、その裏を明かす種明かしを 1 つ対応させる
- 解禁タイミング: 「**その概念に触れた後**」とし、対応 Chapter 以降に表示する
- 例外: 構造の種明かしは複数 Chapter にまたがるもの（コマンド/クエリの分離、等）もある。語単位の 1:1 に収まらず、束ねた後に 1 つ出す
- **A面→B面 の対応そのものは [game-rules/overview.md の命名規約](../game-rules/overview.md) が SSOT**。本ドキュメントは「いつ出すか＝回収タイミング」だけを持つ

> **（注意） 既存 books 資産の扱い**: `books/` は再始動・コンセプト設計より前に作った**非連続な資産**。素材としては使うが、その UX（独立した JS カリキュラムを段階的に教える枠）には**引っ張られない**。
>
> | 資産                                                     | 判定                                                      |
> | -------------------------------------------------------- | --------------------------------------------------------- |
> | 用語集（dictionary）                                     | ✅ 使う（回収マップのリファレンス素材として）             |
> | 各レッスンの説明・コード例                               | 🔁 中身は素材化（構成は踏襲しない）                       |
> | CodeExecuter / safeEval / HighlightCodeEditor / CodeSpan | ✅ 部品として転用（生成コード閲覧・将来のサンドボックス） |
> | 2冊タブ構成・「JS を段階的に教える」導線                 | ❌ 引き継がない（UX を引っ張る本体）                      |
