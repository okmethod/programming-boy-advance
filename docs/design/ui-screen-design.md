# UI 画面設計（画面構成・操作・遷移）

UX レベルデザインが**時間軸（いつ・何を／背骨）**を担うのに対し、本ドキュメントは**空間軸（何を・どこに見せ、どう操作し、どう遷移するか）**を担う。  
詳細は、[ux-level-design.md](./ux-level-design.md) の「ゲーム設計の進め方」を参照。

---

## UI 所掌

**UI 所掌**は、「プレイヤーのどの活動に寄与するか」という役割を、**排他的にグルーピングする単位**。

| UI 所掌          | ミッション（寄与するプレイヤー活動）                   |
| ---------------- | ------------------------------------------------------ |
| オートマトン構築 | 自キャラのプログラム等をカスタマイズする               |
| オートバトル観戦 | 自律対戦を観て、途中経過と結果を確認する               |
| 敵プログラム読解 | 敵キャラの公開プログラムを読み、行動パターンを把握する |
| ステージ進行     | ステージを選び、プレイ画面に遷移する                   |
| レジストリ管理   | レジストリで手持ちオートマトンイメージを管理する       |
| B面解説          | A面の裏にあるB面（実技術・CS 概念）を学ぶ              |

---

## UI コンポーネント

UI コンポーネントは、主要部品の実装単位。  
各コンポーネントは必ず1つの UI 所掌に属する。

| UI 所掌          | コンポーネント名                       | 説明                                                            |
| ---------------- | -------------------------------------- | --------------------------------------------------------------- |
| オートマトン構築 | `BlocklyEditor`                        | ブロックを組むエディタ（パレット含む）                          |
| オートマトン構築 | `CapacityGauge`                        | CP（作成予算）の残量                                            |
| オートバトル観戦 | `BattlePodViewer`                      | バトルポッド盤面                                                |
| オートバトル観戦 | `AutomatonStatusViewer`                | 各オートマトンの HP/BP                                          |
| オートバトル観戦 | `PlaybackController`                   | 実行・再生・一時停止・ステップ                                  |
| オートバトル観戦 | `ResultOverlay`                        | 勝敗（勝ち/負け/引き分け）                                      |
| 敵プログラム読解 | `ProgramViewer`                        | 公開プログラム表示（実行ハイライト付き）                        |
| ステージ進行     | `StageSelectList` / `StageSelectModal` | ステージ選択（一覧＝List／ヘッダーの器＝Modal）・アンロック状況 |
| レジストリ管理   | `RegistryViewer`(仮)                   | 手持ちイメージの一覧・版管理                                    |

## UI 画面遷移

| ルート         | 役割                                                              |
| -------------- | ----------------------------------------------------------------- |
| ステージ進行   | ステージ間の移動・アンロック状況の提示                            |
| プレイ面       | オートマトン構築 ⇄ オートバトル観戦 ＋ 敵プログラム読解           |
| サンドボックス | ステージ非依存で オートマトン構築 ＋ 試運転（勝敗・デプロイなし） |

```
ステージ進行 → [選択] → プレイ面 → [決着] → ステージ進行 へ戻る
                          ↑___________________|（次ステージ／再挑戦）

ホーム → サンドボックス（ステージを選ばず「組む→試運転」だけを回す）
```

- ルートは `src/routes/` 直下に対応。UI コンポーネントは route 構成に引きずられないよう `src/lib/presentation/components/<UI 所掌>/`（`building` / `spectating` / `inspecting` …）に置く
- レジストリ管理は独立 UI 所掌だが専用ルートは持たず、**構築UI内のタブ**として現れる。構築UI（構築エリア＋試運転レール）は共通化し、2つのルートで共有する：
  - **プレイ面**のプログラミング画面＝ステージ文脈つき（参照レールで敵/初期配置を見る・デプロイ（対戦反映）あり）
  - **サンドボックス**＝ステージ非依存（参照なし・デプロイなし・ビルド → 試運転 → プッシュ/プル のみ）
- **ステージ選択は URL が SSoT**。リロード・ディープリンクに耐える。プレイ面はステージ必須なので、動的ルート `/battle-pod/[stage]` の**パスパラメータ**で持つ（query ではない＝ステージ無しの `/battle-pod` は成立せず選択画面へリダイレクト）。
- ステージ id は**順序非依存の安定 slug**（例 `simple-charger`）。表示番号・順序を id に載せないため、将来の並べ替えや Tier/Chapter 階層化で URL が腐らない
- ゲームロジックの単一窓口（`BattleFacade`）は**合成ルートの module singleton**（`presentation/composition.ts`）。具体 Adapter の注入をここ一箇所に閉じ込める

> イメージのライフサイクル（Build → Push/Pull → Deploy）は [overview.md](../game-rules/overview.md) の「オートマトンのライフサイクル」を正とする。UI での割当は下記「イメージのライフサイクル操作」を参照。

## UI 画面レイアウト

### 全ルート共通の外枠

- **ヘッダー（全幅・常設）**: 左＝アプリ名／中央＝現在ページ名／右＝常設ボタン
- **本体**＝各ルートの画面（下記のプレイ面など）

### プレイ面（1ルート）

プレイの中心画面。  
オートマトン構築／オートバトル観戦／敵プログラム読解 の3領域を**1ルートに載せる**。  
`観る → 直す → また観る` の反復を軽くするため、ルート遷移・プログラム状態の受け渡しを挟まない（iPad 横向き・1画面前提）。  
プレイ面は **観戦画面（常時表示）＋プログラミング画面（下部ドロワー）** で構成する。

#### 観戦画面の構成

コードを追うことがゲームの根幹なので、**観戦を既定表示とし、自/敵プログラムは常時出し続ける**。

- **上段**: ステージ案内（ステージ名＋目標）
- **中段（1:2:1）**: 左＝自陣営／中央＝盤面（主役）／右＝敵陣営
  - 左右カラム（陣営）＝ `AutomatonStatusViewer`（上）＋ `ProgramViewer`（下）
  - 中央カラム＝ `BattlePodViewer` ＋ `PlaybackController`。決着時は `ResultOverlay` を盤面へ重ねる
- **下段**: 「プログラミング」ボタン（プログラミング画面を開く）

**概要図**:

```
┌────────────────────────────────────────────┐
│ 上段: [ステージ案内]                          │
│ 中段:                                       │
│┌ 自陣営 ┐┌────── 盤面（主役） ──────┐┌ 敵陣営 ┐│
││status ││                        ││status ││
││-------││      BattlePod         ││-------││
││program││   PlaybackController   ││program││
│└───────┘└────────────────────────┘└───────┘│
│ 下段:  [ プログラミング画面表示ボタン ]         │
└────────────────────────────────────────────┘
```

#### プログラミング画面の構成

構築UIは **構築エリア（左）＋参照レール（右）** の2カラム。構築エリアと試運転レールは
サンドボックス面と共通化する（下記）。

- **構築エリア（左）**: ヘッダー行＝切替タブ（ブロック編集／エディタ編集／レジストリ）＋ `CapacityGauge` ＋ **ビルドボタン**。
  メイン領域＝タブで差し替え（ブロック編集＝`BlocklyEditor`／エディタ編集＝生成コード表示／レジストリ＝`RegistryViewer`）
- **参照レール（右・固定幅）**: 参照（初期配置案内 `BattlePodViewer`＋敵プログラム `ProgramViewer`）⇄ 試運転（相手なし／stub の固定盤で単体実行＝試運転レール）を切替。プレイ面では加えて閉じる（×）を置く

##### イメージのライフサイクル操作（Build / Push / Pull / Deploy）

生の編集（Blockly）は直接は走らない。**ビルドで凍結したイメージ**が試運転・プッシュ・デプロイの対象になる（モデルの正は overview）。UI 上の割当：

- **ビルド**（構築エリアのヘッダー）: 編集を凍結してイメージ化。ビルド済みイメージと編集が乖離したら**「要ビルド（dirty）」**を示し、試運転・デプロイを促す
- **試運転**（参照レール）: **最新のビルドイメージ**を実行（未ビルドなら不可＋ビルド促し）。生の編集は食わない
- **プッシュ / プル / デプロイ**（レジストリタブ＝`RegistryViewer`）: プッシュ＝イメージをレジストリに保存／プル＝保存を編集に戻す（改良の起点）／デプロイ＝イメージを対戦に反映（**プレイ面のみ**。サンドボックスは出さない）

**概要図**:

```
┌[ブロック編集][エディタ編集][レジストリ] CPゲージ [build] │ [参照][試運転] [×]┐
│┌────── メイン領域（タブで差替）──────┐┌─ 参照 or 試運転 ─┐│
││                                 ││ 初期配置＋敵     ││
││  BlocklyEditor ／ 生成コード ／  ││  または          ││
││  RegistryViewer（push/pull/     ││ 試運転盤＋ログ    ││
││   deploy※プレイ面のみ）         ││ （build イメージ） ││
│└─────────────────────────────────┘└─────────────────┘│
└───────────────────────────────────────────────────────┘
```

### サンドボックス面（1ルート）

ステージを選ばず「組む → ビルド → 試運転」だけを回す独立画面。プレイ面のプログラミング画面と
**構築エリア＋試運転レールを共有**し、ステージ文脈（観戦・敵読解・初期配置参照）とデプロイ（対戦反映）を持たない。
プッシュ/プル（保存・ロード）は共有し、ビルド → 試運転 → プッシュ/プル のループを回せる。

- **左**: 構築エリア（プレイ面と同一。CP 上限はステージ非依存の既定値）
- **右**: 試運転レール（参照への切替なし＝試運転に固定）
