# プログラム実行モデル

自キャラ/敵キャラの[プログラム](../game-rules/overview.md#プログラム-program)を、[共通クロック](../game-rules/overview.md#共通クロック-clock-とアクション-action)の下でどう実行するか。

---

## 方針

**プログラム＝命令木（AST）**とし、**ドメイン層の再開可能インタプリタ**が、**1アクションずつ**解釈する。
バトルループは自キャラと敵のアクションを**ロックステップ**で交互に適用し、決定的に勝敗へ進める。

## なぜ（判断の指針）

- **決定的・再現可能**: 「敵の動きを読んで対処する」という看板メカニクスは、敵が毎回同じ動きをする前提で初めて成立する
- **Worker 不要でテスト可能**: ドメイン層が純TSの決定的関数になり、ブラウザなしで Unit テストできる（姉妹PJの `executeTurn(state) => state` 流儀に一致）
- **観戦・デバッグが自然**: 1アクション単位で止められるため、観戦・一時停止・「なぜ負けたか」の追跡ができる
- **共通クロック**: 対戦の公平性とタイミング勝負の前提（[overview.md](../game-rules/overview.md#共通クロック-clock-とアクション-action)）

### 実行の粒度（tick モデル）

採用: **逐次ステップ＋ロックステップ**。インタプリタが「1アクション（move/turn/attack/wait）」ずつ `yield` し、バトルループが自キャラと敵を1アクションずつ交互に適用する。
（却下: 毎クロックで全プログラムを走らせる「一括実行」。細かい interleave が消え、タイミング勝負・予測が粗くなるため）

### 再開可能性の実装

- **JS ジェネレータ**（`function*` で action を yield）で「再開可能」を実現する。小さなツリーウォーク・インタプリタを generator 化すれば足りる
- 明示的バイトコード VM（PC＋スタックの明示シリアライズ）は**不要**。途中状態の保存は要らず、**リプレイは「同じシード＋同じプログラムを頭から再実行」で決定的に再現**できるため
- **決定性のルール**: ドメイン層で wall-clock / 無シードの乱数を使わない。ばらつきが要る場合は**シード付き PRNG を状態に持つ**

## 最小契約（型の骨子）

この4つを固めれば、ストア機構・コンテンツ方式・ブロックUI は後から噛ませられる。
**型の正本（SSoT）はコード**に置き、ここでは骨子だけを示す（シグネチャの転記はドリフト源になるため避ける）。

1. **プログラム＝命令木（`Program` / `Stmt`）**: ブロックUIが出力する AST。`call`（コマンド）/ `repeat` / `if` / `while` の4種で構成する。JS 文字列ではない
2. **世界の状態（`BattleState`）**: 不変・readonly。グリッド・オートマトン・クロック・乱数シード・ログ・勝者を持つ
3. **再開可能インタプリタ（`run`）**: プログラムを1アクション（move / turn / attack / wait）ずつ yield するジェネレータ
4. **バトルループ（`applyTick`）**: 自キャラと敵キャラの1アクションを共通クロックで同時適用し、決定的に勝敗へ進める

センサ（`壁がある?` `敵が近い?` 等）は `BattleState` を読む純粋関数＝決定的。敵プログラムも同じ命令木を流用する。

> 型の定義は [domain/models/types.ts](../../skeleton-app/src/lib/domain/models/types.ts)、公開 API は [domain/index.ts](../../skeleton-app/src/lib/domain/index.ts) が正。本節と食い違う場合はコードを優先する。

## 諦めるもの

- **eval-in-Worker の自由度 / 生 JS 入力**: 現状の `safeWorkerScript.js`（JS を eval して Worker 実行）が持つ「任意の JS が動く」自由度は手放す
- これは将来の「上級者向け生 JS モード」のオプションに格下げする（当面は作らない）。初学者はブロック＝命令木で十分カバーできる
