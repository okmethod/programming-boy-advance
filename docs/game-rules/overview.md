# 世界の全体像

このゲームの世界観・構成要素と、ユビキタス言語を定義する。

---

## 命名規約（Naming Convention）

ユビキタス言語は、**A面/B面の二重構造**で設計する。

- **A面（プレイヤーが触る語）**: 親しみやすい世界観語。**ゲームプレイ画面に出す語はここに絞る**
- **B面（教材で明かす実用語）**: 実際の技術・コンピュータサイエンス概念。A面の裏で 1 対 1 で対応づける

命名の作り方は3タイプ。

- **技術用語**: 実在の技術用語を無改変で使用
  - 例: `デプロイ` / `push` / `pull` / `ビルド` / `VM`
- **一般用語**: 技術専用を、イメージのつきやすい一般用語に置き換えて使用
  - 例: `オートマトン（コンテナ）` / `素体（BaseImage）`
  - 技術用語と見分けがつくよう、このドキュメント上では上記のように技術用語をカッコ書きで併記する
- **造語**: 技術語を合成・加工した固有概念
  - 例: `バトルポッド`（バトル＋Pod）/ `オートマトンイメージ`（オートマトン＋コンテナイメージ）/ `オートマトンレジストリ`（オートマトン＋コンテナレジストリ）
  - 技術用語・一般用語と見分けがつくよう、このドキュメント上では `オートマトンイメージ（造語）` のように造語ラベルをつける

> 方針: 技術用語を並べすぎず、適宜一般用語や造語を使ってバランスを取る。  
> 簡易なものであれば技術用語をそのまま A面で出しても良いが、裏側の概念は B面として別途解説する。

---

## 実行環境の4層（Execution Stack）

世界は「物理マシン → 仮想マシン → バトルポッド（造語） → オートマトン（コンテナ）」という**入れ子の実行環境**として捉える。  
各層がゲームのスケールに対応する。

```
物理マシン（実機）    … プレイヤーの端末。プログラムを書き、デプロイする
  └ 仮想マシン（VM）  … コンテナの実行基盤（ホスト）。この上にバトルポッドが立つ
    └ バトルポッド   … 対戦空間。両オートマトンが同居（立てる＝試合開始／落とす＝終了）
      └ オートマトン … 自律稼働する個体
```

> この入れ子により「物理 vs 論理」の対立は解消する。物理マシンはプレイヤー自身の現実の層として外側に置き、ゲームは論理マシンの中の世界とする。  
> バトルポッドは仮想空間であり、オートマトンは**仮想空間で走る「論理プロセス」**（物理機体ではない）。  
> コンテナの資源制限を基礎リソースとして、撃破はプロセスの停止として捉える、のように実機能がそのままゲーム機構になる。

---

## バトルポッド（造語）

試合の場となる格子状（グリッド）の盤面。  
VM 上に立ち上がり、両オートマトンが同居する。

- **セル**: 盤面の1マス。ポッド内の共有空間（メモリ＋ボリューム）に相当する
- **辺**: セルとセルの間の境界線。通行可能なら道、通行不可なら壁となる
- **エンティティ（Entity）**: バトルポッド上の対象物。盤面のどこに配置されているかの位置情報を持つ。オートマトンとファイル（後述）

---

## オートマトン（コンテナ）

プログラムで自律行動するエンティティの総称＝この世界の**種族名**。  
位置に加え向きを持つ。

技術的実体は**コンテナ**相当として扱い、**素体＋プログラム**で構成される個体を指す。

- **素体（BaseImage）**: オートマトンの土台＝ベースイメージ＋資源割当（cgroups）。これに `プログラム` 層を乗せてビルドすると `オートマトンイメージ` になる。資源割当が基礎リソース（後述）を定める＝「どれだけ戦えるか／どれだけ書けるか」の器
- **プログラム（Program）**: 素体に焼き込む振る舞い＝中で走るコード（命令木）。プレイヤーはこれを書いてカスタムする（→ 後述の「プログラム」）

陣営による区別（どちらもオートマトン）:

- **自キャラ（Ally）**: プレイヤーのオートマトン。プレイヤーが書いたプログラムで自律行動する
- **敵キャラ（Enemy）**: 決定的なプログラムで自律行動する。移動チュートリアルでは「動かない敵（的）」として登場する

勝利条件・攻撃・決着などの戦闘ルールは [auto-battle.md](./auto-battle.md) を正とする。

### オートマトンの基礎リソース

素体の資源割当（cgroups）に応じた**3つのリソース**を持つ。  
増減ルール・勝敗判定は [auto-battle.md](./auto-battle.md) を正とする。

- **HP（ヒープポイント）**: 体力。尽きる（0）と撃破される。B面＝ヒープ領域（メモリ）
- **BP（ビジーポイント）**: 処理負荷。溜まって上限に達すると一時的に行動不能。B面＝CPU（ビジー状態）
- **CP（プログラムキャパシティ）**: 書けるコード量の上限（戦闘ゲージではなく作成予算）。B面＝コードセグメント（メモリ）

### オートマトンのライフサイクル（Build → Deploy → Battle）

オートマトンは「書く → ビルド → 保管 → デプロイ → 稼働」の流れで生まれる。  
実際のコンテナ運用をそのまま下敷きとしている。

```
素体（BaseImage） ＋ プログラム
  → ビルド → オートマトンイメージ（未デプロイの成果物・不変）
  → push → オートマトンレジストリ（手持ち／編成。タグでバージョン管理）
  ──（対戦開始）──
  → pull → バトルポッド に デプロイ
  → 稼働インスタンス＝コンテナ ＝ オートマトン（盤上）
```

- **オートマトンイメージ（造語）**: ビルド済み・未デプロイの静的な姿（手持ちに並ぶ個体）
- **オートマトンレジストリ（造語）**: ビルド済み `オートマトンイメージ` の保管庫＝プレイヤーの手持ち／編成。**イメージタグでバージョン管理**でき、改良を重ねる（`v1`→`v2`…）／前版に戻す（rollback）が自然に表現できる
- **ビルド / push / pull / デプロイ**: エンジニアの日常語をそのまま世界観語に採用（「見慣れないがかっこいい語」の収穫）

## プログラム（Program）

プレイヤーが自キャラに与える行動の指示。  
ゲームの核心は、敵プログラムの振る舞いを読み解き、それに勝つプログラムを書くこと。

- **命令木**（順次・くりかえし・条件分岐の組み合わせ）として表現する。
- 対戦の再現性・公平性のため、全エンティティは**共通クロック**の下で進む。
- 敵も同じ形式の**決定的プログラム**を持つ。

### プログラムブロック（Program Block・造語）

プレイヤーがオートマトンのプログラムを組む際の構成要素の総称。  
一覧（JP↔EN）は [program-blocks.md](./program-blocks.md) 参照。

- **コマンドブロック（Command Block）**: バトルポッドの状態を**変える**操作。各クロックで各エンティティは**1コマンド**を実行する。
  - 例: `move`（前に進む） / `turn`（向きを変える） / `attack`（攻撃する） / `wait`（待機）
- **クエリブロック（Query Block）**: バトルポッドの状態を**読む**純粋な問い合わせ。状態を変えず、同じ状態に対して常に同じ答えを返す。条件分岐の判断材料になる。
  - 例: `壁がある?`（wall ahead） / `敵が近い?`（enemy ahead） / `敵の向き`（enemy direction）
- **制御ブロック（Control Block）**: コマンド／クエリを組み立てる骨格（命令木の構造）。置くのは くりかえし・条件分岐 の2種（順次は暗黙）。
  - 例: `くりかえし`（repeat） / `条件分岐`（if）

> **A面（ブロックUI）/ B面（種明かし）の対応**:
>
> - A面はすべて「ブロック」。**コマンドブロック**（する）／**クエリブロック**（調べる）／**制御ブロック**（くりかえし・条件分岐）の3ファミリー。
> - B面で、 **コマンド（変える）/ クエリ（読む）の分離＝ CQS（Command–Query Separation）** と **文（statement）＝コマンド＋制御構文 ／ 式（expression）＝クエリ** について明かす（命令木＝AST、文/式＝ノード種別）。

## ファイル

バトルポッド上の、オートマトン以外の静的・半静的なエンティティの総称。  
位置を持つが向きは持たない。

技術的実体は**共有空間（メモリ＋ボリューム）上のファイル**。  
オートマトンが読む・実行することで盤面に作用する**仕掛け**となる。

盤上の仕掛けの例:

- **クレデンシャル**: 情報開示、閉じていた経路が開く、等
- **スクリプト**: 特定の処理（移動・罠）が起動する、等
- **パッチ**: HP を増強する、等

> 具体的な効果・登場ステージは暫定。要るステージが来たら確定する（YAGNI）。
