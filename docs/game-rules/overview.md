# 世界の全体像

このゲームの世界観・構成要素と、ユビキタス言語を定義する。

---

## 命名規約（Naming Convention）

ユビキタス言語は、**A面/B面の二重構造**で設計する。

- **A面（プレイヤーが触る語）**: 親しみやすい世界観語。**ゲームプレイ画面に出す語はここに絞る**
- **B面（教材で明かす実用語）**: 実際の技術・コンピュータサイエンス概念。A面の裏で 1 対 1 で対応づける

命名の作り方は3タイプ。

- **技術用語**: 実在の技術用語を無改変で使用
  - 例: `デプロイ` / `push` / `pull` / `ビルド` / `VM`
- **一般用語**: 技術専用を、イメージのつきやすい一般用語に置き換えて使用
  - 例: `オートマトン（コンテナ）` / `素体（BaseImage）`
  - 技術用語と見分けがつくよう、このドキュメント上では上記のように技術用語をカッコ書きで併記する
- **造語**: 技術語を合成・加工した固有概念
  - 例: `バトルポッド`（バトル＋Pod）/ `オートマトンイメージ`（オートマトン＋コンテナイメージ）/ `オートマトンレジストリ`（オートマトン＋コンテナレジストリ）
  - 技術用語・一般用語と見分けがつくよう、このドキュメント上では `オートマトンイメージ（造語）` のように造語ラベルをつける

> 方針: 簡易なものであれば技術用語をそのまま A面で出しても良いが、専門用語が並ぶとわかりづらくなるので、適宜一般用語や造語を使ってバランスを取る。裏側の概念は B面で解説する。

## 実行環境の3層（Execution Stack）

世界は「物理マシン → 仮想マシン → バトルポッド（造語） → オートマトン（コンテナ）」という**入れ子の実行環境**として捉える。  
各層がゲームのスケールに対応する。

```
物理マシン（実機）    … プレイヤーの端末。プログラムを書き、デプロイする
  └ 仮想マシン（VM）  … コンテナの実行基盤（ホスト）。この上にバトルポッドが立つ
    └ バトルポッド   … 対戦空間。両オートマトンが同居（立てる＝試合開始／落とす＝終了）
      └ オートマトン … 自律稼働する個体
```

> この入れ子により「物理 vs 論理」の対立は解消する。物理マシンはプレイヤー自身の現実の層として外側に置き、ゲームは論理マシンの中の世界とする。
> バトルポッドは仮想空間であり、オートマトンは**仮想空間で走る「論理プロセス」**（物理機体ではない）。
> コンテナの資源制限を耐久値・コードキャパシティとして、撃破はプロセスの停止として捉える、のように実機能がそのままゲーム機構になる。

## 用語

### バトルポッド（造語）

試合の場となる格子状（グリッド）の盤。  
VM 上に立ち上がり、両オートマトンが同居する。各マスは通行可能/壁などの性質を持つ。  
ここに複数の**エンティティ**が存在し、**共通クロック**の下で行動する。

### エンティティ（Entity）

バトルポッド上の対象。少なくとも位置と向きを持つ。

- **オートマトン（コンテナ）**: プログラムで自律行動するエンティティの総称（この世界の種族名）。自キャラ・敵キャラはいずれもオートマトン
- **壁 / アイテム**: バトルポッド上の静的・半静的な対象

### オートマトン（コンテナ）

プログラムで自律行動するエンティティの総称＝この世界の**種族名**。  
技術的実体は**コンテナ**相当として扱う。  
素体（ベースイメージ）に自律プログラムを焼き込んでビルドし、バトルポッドにデプロイされた個体を指す。
**素体（BaseImage） ＋ プログラム（Program）** の二層で構成される。

- **素体（BaseImage）**: オートマトンの土台＝ベースイメージ＋資源割当（cgroups）。これに `プログラム` 層を乗せてビルドすると `オートマトンイメージ` になる。耐久値・コードキャパシティといった基礎値を定める（＝「どれだけ戦えるか／どれだけ書けるか」の器）
- **プログラム（Program）**: 素体に焼き込む振る舞い＝中で走るコード（命令木）。プレイヤーはこれを書いてカスタムする（→ 後述の「プログラム」）

陣営による区別（どちらもオートマトン）:

- **自キャラ（Ally）**: プレイヤーのオートマトン。プレイヤーが書いたプログラムで自律行動する
- **敵キャラ（Enemy）**: 決定的なプログラムで自律行動する。移動チュートリアルでは「動かない敵（的）」として登場する

### オートマトンのライフサイクル（Build → Deploy）

オートマトンは「書く → ビルド → 保管 → デプロイ → 稼働」の流れで生まれる。実際のコンテナ運用がそのまま下敷き。

```
プログラム ＋ 素体（ベースイメージ）
  → ビルド → オートマトンイメージ（未デプロイの成果物・不変）
  → push → オートマトンレジストリ（手持ち／編成。タグでバージョン管理）
  ──（対戦開始）──
  → pull → バトルポッド に デプロイ
  → 稼働インスタンス＝コンテナ ＝ オートマトン（盤上）
```

- **オートマトンイメージ（造語）**: ビルド済み・未デプロイの静的な姿（手持ちに並ぶ個体）
- **オートマトンレジストリ（造語）**: ビルド済み `オートマトンイメージ` の保管庫＝プレイヤーの手持ち／編成。**イメージタグでバージョン管理**でき、改良を重ねる（`v1`→`v2`…）／前版に戻す（rollback）が自然に表現できる
- **ビルド / push / pull / デプロイ**: エンジニアの日常語をそのまま世界観語に採用（「見慣れないがかっこいい語」の収穫）

### 共通クロック（Clock） とアクション（Action）

対戦の再現性・公平性のため、全エンティティは**共通クロック**の下で進む。
各クロックで各エンティティは**1アクション**を行う（ロックステップ）。

アクションはバトルポッドの状態を**変えうる**。

- 例: `move`（前に進む） / `turn`（向きを変える） / `attack`（攻撃する） / `wait`（待機）

### センサ（Sensor）

バトルポッドの状態を読む純粋な問い合わせ。条件分岐の判断材料になる。  
センサは状態を**変えない**。同じ状態に対して常に同じ答えを返す。

- 例: `壁がある?`（wall ahead） / `敵が近い?`（enemy in range） / `敵の向き`（enemy direction）

### プログラム（Program）

プレイヤーが自キャラに与える行動の指示。  
**命令木**（順次・くりかえし・条件分岐の組み合わせ）として表現する。  
敵も同じ形式の**決定的プログラム**を持つ。  
ゲームの核心は、敵プログラムの振る舞いを読み解き、それに勝つプログラムを書くこと。

### 勝敗（Victory）

**敵の撃破**を勝利条件とする。  
移動チュートリアルも「動かない敵の撃破」に統一する。

## 進行の2軸（学習曲線＝レベルデザイン）

プレイヤーの能力は2つの軸で段階的に拡張され、これがそのままカリキュラムになる。

1. **コマンド・アンロック（何ができるか）**: 取れる行動・使える制御構文が段階的に解放される
   （移動 → くりかえし → センサ → 条件分岐 → 攻撃 → 敵センサ → 決定的に動く敵 → 複雑な敵プログラム）
2. **コードキャパシティ（どれだけ書けるか）**: 書けるコード量に上限があり、進行で増える（遊戯王GBの「デッキキャパシティ」型）。
   「前に進む×10」で上限に達する → くりかえしなら収まる、という形で**抽象化の動機を定量化**する

ステージの並び順そのものが学習曲線であり、1ステージ1概念をバトルポッドの地形とアンロックで強制する。
