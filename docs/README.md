## 💡 プロジェクトコンセプト

### 課題と目的

**課題**:

- 「教育 × ブロック × ブラウザ」のプログラミング学習は、迷路などの**静的パズルで打ち止め**になりがち（Blockly Games / Lightbot / Code.org）
- 「プログラミング × 対戦」の面白さを持つ先行作は、**古い・据置/PC/mobile・テキスト/フローチャート・ゲーム主軸で教育目的でない**（Carnage Heart / Robocode / Gladiabots）
- 両者の良いとこ取り（ブラウザ即プレイ・ブロック・プログラミング前面・学習目的の「対戦」）は**空白**

**目的**:

- ブラウザで、ブロックを組んで**自律キャラを戦わせる**プログラミング学習ゲームを提供する

### コンセプト

**相手のプログラムを読み解いて、それに勝つプログラムを書く対戦型プログラミング学習ゲーム**

- プレイヤーは自キャラの行動プログラムをブロックで組み、あとは**共通クロックの下で自律戦闘を観戦**する
- 取れるコマンドと書けるコード量が**段階的にアンロック**され、それが学習曲線＝レベルデザインになる
- 相手は人間ではなく**決定的に動くプリセット敵**。観察 → プログラムを推理 → 対抗プログラムを書く、という「解ける設計パズル」になる
- 移動チュートリアルも「ゴール到達」ではなく「**敵撃破**」に統一し、最初から対戦の文脈に乗せる

## 🔍 スコープ方針

### やること (In Scope)

- 対戦空間のワールドモデル（グリッド・エンティティ・共通クロック）
- 自律プログラムの決定的実行（命令木 ＋ 再開可能インタプリタ）
- ブロックUI（命令木を出力）と、組んだプログラムの生成コード閲覧
- 決定的なプリセット敵との対戦、勝敗判定（敵撃破）
- 2つのアンロック軸（コマンド解放 / コードキャパシティ）

### やらないこと (Out of Scope)

- 人間同士のリアルタイム対戦（PvP）・マッチング
- 生 JS の自由入力（将来の上級モード候補。当面はブロック＝命令木に限定）
- サーバー/アカウント（永続化は localStorage の範囲）
- 迷路エディタ等の重いオーサリング機能

## 🗂️ ドキュメント構成

ドキュメントを **「何を作るか（問題領域）」** と **「どう作るか（アプローチ）」** の2軸で分ける。

```
docs/
├── README.md      # 全体概要（本ドキュメント）
├── game-rules/    # 何を作るか: このゲームのルール・世界（FW非依存・不変）
└── design/        # どう作るか: このアプリをどう設計・実装するか
```

### ドキュメント間の依存ルール

クリーンアーキテクチャの依存ルールをドキュメントにも適用する。  
**依存の矢印は常に `game-rules/`（内側・安定）に向かう。逆向きは禁止。**

- **`game-rules/`** はこのゲームのルール・世界そのものだけを記述する（実装識別子・パス・実装状況を書かない）。概念の正式名称（ユビキタス言語）を定義するのはここの役割。
- **`design/`** は `game-rules/` を参照してよい。ルールを再説明せずリンクで誘導する。
